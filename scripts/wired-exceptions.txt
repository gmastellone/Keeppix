# origin Phase 10 Task 16. Actually closed on August 27 — this was three
# different features behind a single entry, paid off one at a time
# because their technical shape wasn't the same.
#
# LibraryScan (August 26): `POST /libraries/{id}/scan` responds `202`
# with an `operation_id` immediately (a real background job) — in
# `ProblemsView.vue`, a successful connection retry (`retryConnection`)
# kicks off a real scan and follows its `operation.progress` over the
# WebSocket with a real progress bar and a `[Cancel]` that genuinely
# calls this route (`api/operations.ts::cancelOperation`).
#
# BulkRename (August 27): reversed Phase 9's original design — no longer
# synchronous within the HTTP request. `POST /assets/batch/rename` only
# does the fallible checks up front (permission/visibility), creates the
# `Operation`, and enqueues `JobKind::BulkRename` (`keeppix-jobs::
# rename_batch`, new), responding `202` with an `operation_id`
# immediately just like `LibraryScan`. `RenameFormulaDialog.vue` shows
# real progress plus a working `[Cancel]` while the batch runs. Accepted
# tradeoff: the precise per-asset failure reason (e.g. `"collision"`) no
# longer survives to the caller once it's in the background — the same
# limitation `LibraryScan` already has (only `succeeded`/`done`/`total`
# remain readable on the `Operation`, never the reason for an individual
# failure). Found and closed in the same piece of work, a pre-existing
# gap discovered here: `OperationStatus::Failed` had existed since Phase
# 10 but no path ever wrote it (`OperationsRepo::finish_failed`, new) — a
# tracked job that failed stayed `running` forever. The same gap remains
# open in `discover.rs`/`embed.rs`/`detect_faces.rs`
# (`LibraryScan`/`AiAnalysis`/`FaceDetection`), not touched here.
# `undo_batch` was out of scope for this change — stayed synchronous,
# `track_operation: bool` untouched: same scaling limitation, a separate
# debt. Closed later — see the RenameUndo entry below.
#
# RenameUndo: closed the `undo_batch` debt above the same way `apply_batch`
# was fixed. `POST /assets/batch/rename/{batch_id}/undo` only does the
# fallible check up front (`RenameRepo::assert_batch_owned`, a plain
# `SELECT`, not the row lock the real undo takes), creates the `Operation`,
# and enqueues `JobKind::RenameUndo` (`keeppix-jobs::rename_undo`, new),
# responding `202` with an `operation_id` immediately — same shape as
# `BulkRename`. `RenameRepo::undo` no longer creates its own `Operation`:
# it takes `operation_id: Option<OperationId>` instead of the old
# `track_operation: bool`, exactly mirroring `apply`'s earlier change.
#
# AiAnalysis/FaceDetection (August 27, view-only): no HTTP route triggers
# them (automatic background windows) — built `MoreView.vue`, a
# "Background activity" section, view-only (no pause/cancel, by explicit
# choice) that reads `phase` from `operation.progress`
# ("embedding"/"detecting", the only values these two jobs actually set)
# to tell them apart from `LibraryScan`/`BulkRename`, which already have
# their own surface elsewhere.

# origin Phase 4 (maps/geotagging). Decision made on August 26, no longer
# deferred — the four were grouped together but are not the same case:
#
# get_for_user (home.rs) and timezone_changes (geo.rs) were genuinely
# dead duplicates — zero calls anywhere, not even in tests (verified with
# grep across the whole `crates/` tree). `get_for_user` duplicated

# — the real preview path goes through
# `GeoRepo::timezone_change_preview`, yet a third name. Both removed, no
# longer exceptions.
#
# timezone_for and apply_taken_at_batch, on the other hand, are NOT dead:
# same case as `count_by_status` above. `timezone_for` and the real
# `timezone_candidates_sql()` (behind `apply_timezone_changes`, wired)
# both call `timezone_match_sql()` — the same `ST_Covers` spatial
# predicate. The `timezone_for` tests in `tests/geo.rs` (Tokyo found,
# ocean not found, a point on a shared boundary with no double match and
# no error) are the only real coverage of that predicate — `tests/
# timezones.rs` (the real path) only verifies permissions/authentication,
# never the boundary geometry. `apply_taken_at_batch` and the real
# `apply_timezone_changes` both call
# `apply_taken_at_assignments_in_transaction`; the `apply_taken_at_batch`
# test in `tests/overrides.rs`
# (`timezone_writer_preserves_a_taken_at_override_present_at_write_time`)
# is the only coverage of the rule "a prior manual override must not be
# overwritten by a bulk timezone correction" — not replicated elsewhere.
# Deleting them would lose real coverage on production code with no
# equivalent replacement: they stay as tested internal APIs, with no
# HTTP route of their own, permanent exceptions.
fn timezone_for permanent
fn apply_taken_at_batch permanent
